# Characterising xc7s25 (Arty S7-25)

`prjxray-db` ships nothing for xc7s25: no `tilegrid.json`, no `part.yaml`, no
`mapping/` entry. It is a genuinely different die from xc7s50, so there is no
alias to borrow — nextpnr cannot be pointed at the s50 database and told to
pretend. This is the job that produces the missing data.

Part: **`xc7s25csga324-1`** (what the Arty S7-25 carries).
Config: `source env/xray_env.sh spartan7_s25`.

## What actually has to be produced

Segbits are *not* on the list. They are family-level and already exist for
spartan7, because the Series-7 tile types are shared — which is exactly what
`010-clb-lutinit` demonstrated when it reproduced identical `LUT.INIT` bits on
all seven devices. What is missing is everything **device**-specific:

| Artefact | Fuzzer | Why it is device-specific |
| --- | --- | --- |
| `part.yaml`, `part.json` | `001-part-yaml` | IDCODE and per-column frame counts |
| `tilegrid.json` | `005-tilegrid` | frame base addresses and word offsets |
| `tileconn.json`, `node_wires.json` | `072`/`074` | wire graph; offline in RapidWright |
| package pins | `update_resources.tcl` | **done** — see below |

## Writable database overlay

The tree's standing rule is that `prjxray-db` is a read-only reference. But both
`001` and `005` have `pushdb` targets that `cp` into `${XRAY_FAMILY_DIR}`, and
`005`'s Makefile symlinks `${XRAY_DATABASE_DIR}/<family>/mapping` into its
`basicdb`. A part that is absent upstream therefore needs a database directory
that is writable *and* still carries the family-level files.

`env/mk_db_overlay.sh` builds one at `../xray-db-local`: every entry is a
relative symlink back into `prjxray-db`, except

* `spartan7/mapping/` — a real copy, because `create_environment.py` resolves a
  part through `mapping/parts.yaml` (package, speedgrade) and
  `mapping/devices.yaml` (device to fabric), and xc7s25 has to be registered in
  both;
* `spartan7/xc7s25/` and `spartan7/xc7s25csga324-1/` — real directories, where
  the fuzzer output lands.

Reading the overlay is identical to reading `prjxray-db`; nothing written
through it can reach the reference. `settings/spartan7_s25.sh` exports
`XRAY_DATABASE_DIR` at it. That works because `env/xray_env.sh` evaluates the
settings file's `export XRAY_` lines *after* setting its own default and
*before* deriving `XRAY_FAMILY_DIR` and `XRAY_PART_YAML`, so the override
reaches all three. Every other config still resolves to `prjxray-db`, which is
worth re-checking after any change here:

```bash
source env/xray_env.sh spartan7 && echo $XRAY_DATABASE_DIR   # .../prjxray-db
```

## Vivado

**2026.1.1**, the Linux install at `/mnt/e/Xilinx/2026.1.1/Vivado`, driven
natively. Despite sitting on a Windows drive it is a Linux build — a bash
`vivado`, `settings64.sh`, an `lnx64/` tree and its own `Xilinx_wsl.lic` — so
`env/vivado.sh` sources the settings script and execs it directly. The whole
WSL→Windows layer (`cmd.exe`, `wslpath -w`, `WSLENV`) is bypassed, which removes
a class of failure rather than working around it; the Windows path is still there
behind `XRAY_VIVADO_LINUX=""`.

It supports the part. A smoke test reports version `2026.1.1`,
`link_design -part xc7s25csga324-1` succeeds, and Vivado's own part database
gives `IDCODE 0x037c4093` — an independent confirmation of the value the
bitstream yields.

The earlier work on this part (the package pins, and the first `001` run) used
the **Windows 2024.2** install. The switch was made mid-way, so the two versions
could be compared directly, and they agree completely:

* both report **3650 SLICE sites** on this die;
* `001` re-run end to end under 2026.1.1 produces `part.yaml` and `part.json`
  **byte-identical** to the 2024.2 output.

That is the cross-check worth having. Two Vivado major versions, on two
different operating systems, through two entirely different launch paths
(`cmd.exe` + `WSLENV` vs. a native exec), independently produce the same IDCODE
and the same 75-column, 3060-frame configuration layout. Frame addresses are
silicon facts rather than toolchain artefacts, and now there is evidence rather
than an assumption.

All nine parts the tree targets (`xc7a50t`/`100t`/`200t`, `xc7k70t`/`160t`,
`xc7s50`, `xc7s25`, `xc7z010`/`z020`) are present in 2026.1.1, so making it the
wrapper default does not strand the other configs. The `010-clb-lutinit` results
in the top-level README were produced under 2024.2 and have not been re-run.

## Running order

### 0. Package pins — done

`work/s25/pins.json` was extracted with `update_resources.tcl` (Vivado 2024.2.2,
`link_design -part xc7s25csga324-1`). It is cached into the resources workflow
as `work/resources/spartan7__xc7s25csga324-1.json`, and the part is listed in
`env/gen_resources.sh`, so re-running that script merges it without calling
Vivado again. Result, by the same selection rule upstream uses
(`clk[0]`, `dat[0]`, `dat[len/2]`, `dat[-1]`):

```
xc7s25csga324-1:  pins: {0: P14, 1: L13, 2: F14, 3: P7}
```

### 1. `001-part-yaml`

```bash
source env/xray_env.sh spartan7_s25
cd ../prjxray/fuzzers/001-part-yaml && make database
```

Vivado synthesises `top.v`, places, routes, and writes two bitstreams: a normal
one and a `BITSTREAM.GENERAL.PERFRAMECRC YES` one that emits each frame followed
by its address, exposing the gaps in the frame address space.
`gen_part_base_yaml` then reads the per-frame bitstream into `part.yaml`.

`generate.tcl` reads only `XRAY_PART` and `XRAY_PIN_00..03`, all of which
`env/vivado.sh` already forwards across the WSL→Windows boundary, so no wrapper
change was needed.

> An earlier hand-rolled attempt at a `part.yaml` for xc7z007s
> (`work/z007s_ref/`) died with *"No LOUT or FAR writes found. Was
> BITSTREAM.GENERAL.DEBUGBITSTREAM or BITSTREAM.GENERAL.PERFRAMECRC set to
> YES?"* and left an empty `derived_part.yaml`. The stock fuzzer sets
> `PERFRAMECRC` itself, which is the difference.

**Result: done and verified.** `idcode: 0x37c4093`, 75 configuration columns,
3060 frames. Three independent checks, all agreeing:

* **IDCODE** matches `0x037C4093` as derived from `IDCODE_REGISTER` in
  `<vivado>/data/parts/xilinx/spartan7/public/bsdl/xc7s25_csga324.bsd`
  (version `XXXX`→0, family `0011011`, array size `111000100`, manufacturer
  `00001001001`, trailing `1`). The same decomposition reproduces xc7s50's
  published `0x0362F093` and the family field matches, so the method is sound.
* **`bitread` round trip** — the load-bearing one. Reading Vivado's own
  `design.bit` against the new `part.yaml` resolves every frame address and
  reports exactly 3060 configuration frames, the same total the yaml's
  per-column `frame_count`s sum to. A wrong frame address map would not parse.
* **Scale** — 75 columns / 3060 frames against xc7s50's 134 / 5408 is 0.56,
  consistent with 42 SLICE columns against 66+58.

`part.json` carries iobanks `{0: X1Y78, 14: X1Y26, 15: X1Y78, 34: X100Y26}`.
Both files are pushed to `xray-db-local/spartan7/xc7s25csga324-1/`;
`prjxray-db` was verified untouched afterwards.

One harness fix fell out of this. `001`'s Makefile runs
`python3 -m utils.xyaml`, but prjxray's `setup.py` declares
`packages=['prjxray']`, so the editable install never exposes the sibling
`utils` package and the step died with `ModuleNotFoundError`. `env/xray_env.sh`
now puts `XRAY_DIR` on `PYTHONPATH`; it is the only fuzzer that imports `utils`,
but the fix is general.

### 2. `005-tilegrid`

The long one. Needs geometry that `spartan7_s25.sh` deliberately does not yet
set. From RapidWright, offline (`java/com/hotwright/rwfuzz/DeviceExtents.java`,
output in `work/s25/extents.txt`) — note these are **per-column** extents, not a
bounding box, and on this die the difference is not cosmetic:

```
tile grid   102 columns x 105 rows
SLICE       X0..X33  Y0..99      X34..X41 Y0..49
RAMB18      X0..X1   Y0..39      X2       Y0..19
RAMB36      X0..X1   Y0..19      X2       Y0..9
DSP48       X0..X1   Y0..39
```

xc7s25 is **L-shaped**: the right-hand eight SLICE columns stop half way up. A
bounding-box `SLICE_X0Y0:SLICE_X41Y99` would claim about 400 sites that do not
exist. xc7s50 has the same trap in its own settings file, which is why it splits
RAMB18 into `X0Y0:X1Y59` plus `X2Y0:X2Y39`. So:

```
XRAY_ROI_TILEGRID="SLICE_X0Y0:SLICE_X33Y99 SLICE_X34Y0:SLICE_X41Y49 \
                   RAMB18_X0Y0:RAMB18_X1Y39 RAMB36_X0Y0:RAMB36_X1Y19 \
                   RAMB18_X2Y0:RAMB18_X2Y19 RAMB36_X2Y0:RAMB36_X2Y9 \
                   DSP48_X0Y0:DSP48_X1Y39"
```

It is also a single clock-region-row-pair device: SLICEs run Y0..99 with no
second bank, unlike xc7s50's `SLICE_X0Y0:SLICE_X65Y99` *plus*
`SLICE_X0Y100:SLICE_X57Y149`.

The sub-fuzzers `005`'s Makefile builds unconditionally for spartan7 all have
their sites present on this die — `XADC` (monitor), `MMCME2_ADV`, `PLLE2_ADV`,
BRAM, DSP, and the `CFG_CENTER_*`, `CLK_BUFG_*`, `CLK_HROW_*`, `HCLK_IOI3`,
`CMT_TOP_*` tile types — so none of them should fail for want of a site.

`XRAY_ROI` and `XRAY_ROI_GRID_*` are **not set, on evidence**. 005's README
calls `XRAY_ROI` mandatory, but nothing under `fuzzers/005-tilegrid/` reads the
bare variable, and `XRAY_ROI_GRID_*` occurs in that README and nowhere else in
the tree. The only geometry 005 actually consumes is `XRAY_ROI_TILEGRID` and
`XRAY_EXCLUDE_ROI_TILEGRID`.

`XRAY_EXCLUDE_ROI_TILEGRID` is empty here (no site on this part is known to
resist locking; upstream needs it only for artix7_200t) but it must still be
**set**, and that exposed a latent bug in `env/vivado.sh`.
`util.tcl:make_project_roi` reads `$::env(XRAY_EXCLUDE_ROI_TILEGRID)` with no
`info exists` guard, while the wrapper skipped any variable failing `-n`, so an
empty one never crossed to Windows. Worse, Windows cannot hold an empty
environment variable at all — `set VAR=` deletes it — which was confirmed
directly:

```
$ export T_EMPTY="" T_SPACE=" "; WSLENV=T_EMPTY:T_SPACE cmd.exe /c "echo [%T_EMPTY%] [%T_SPACE%]"
[%T_EMPTY%] [ ]
```

The wrapper now tests `-v` instead of `-n` and substitutes a single space for an
empty value, which keeps the variable defined and still iterates zero times in
`foreach roi $::env(...)`. This affects `settings/spartan7.sh` too — it sets the
same variable to `""` — so the fix is general, not an s25 special case. `010`
never hit it because its Tcl does not read that variable.

### The `cfg` sub-fuzzer is broken on modern Vivado

`cfg` fails and produces no tdb. **This is not caused by the version switch and
not specific to xc7s25** — it is a pre-existing incompatibility between prjxray
and any Vivado newer than the 2017.2 it pins.

`cfg/top.py` LOCs a `BSCANE2` to `BSCAN_X0Y0` and fuzzes its `JTAG_CHAIN`
attribute between `"1"` and `"2"`. Modern Vivado requires chain *n* to sit at
`BSCAN_X0Y(n-1)`, so every specimen with the `"2"` state dies in DRC:

```
ERROR: [DRC PDRC-2] BSCAN_JtagChain: Unsupported programming for BSCAN site
BSCAN_X0Y0 and JTAG_CHAIN attribute value 2.
ERROR: [Vivado 12-1345] Error(s) found during DRC. Bitgen not run.
```

specimen_001 (`JTAG_CHAIN("1")`, tag value 0) passes; specimen_002
(`JTAG_CHAIN("2")`, tag value 1) fails — and the fuzzer needs both states to
solve anything. **Verified on both toolchains**: the same specimen re-run under
the Windows Vivado 2024.2 install fails with the identical DRC, so 2026.1.1 is
exonerated. We had simply not reached `cfg` during the 2024.2 run. No other
sub-fuzzer touches BSCAN; `cfg_int`, which covers the INT tile beside the
config centre, is unaffected.

**Consequence, and why it is survivable.** `add_tdb.py` skips a missing tdb
silently, and `generate_full.py` guards every walk with
`if not tile['bits']: continue`, so the build completes and `CFG_CENTER_MID`
simply ends up with no frame address. That is enough for logic, routing and IO —
what a chipdb and a blinky need — but it means no FASM can be emitted for
config-centre features (BSCAN, STARTUP, ICAP, DNA_PORT).

**A promising fix that does not work.** Disabling the offending DRC is idiomatic
in this very fuzzer family — `pll`, `gtp_channel` and `dsp_int` all do
`set_property IS_ENABLED 0 [get_drc_checks {...}]` before `write_bitstream`.
Adding `PDRC-2` to `cfg/generate.tcl` looked ideal because it changes nothing
about the experiment: same site, same attribute, same expected bit, so the pinned
`--dword 67 --dframe 1B --dbit 18` deltas stay valid.

It was tried and **rejected on measurement**. `write_bitstream` does then
complete, and the netlist genuinely carries the attribute
(`Parameter JTAG_CHAIN bound to: 2`), but the resulting configuration frames are
*identical* to the `JTAG_CHAIN("1")` specimen:

```
unfiltered bitread:      10 bits vs 10 bits
frame-data differences:  0
.bit byte differences:   5, all at offsets 184-190 (header: design name, timestamp)
```

Modern Vivado accepts the attribute and simply does not encode it. So the patch
converts a loud failure into a **silent no-op**: segmatch would find no
distinguishing bit and emit an empty or meaningless tdb. That is strictly worse
than failing, so the patch was reverted and `cfg/generate.tcl` is stock again.

Note the trap — `write_bitstream completed successfully` was not evidence the
fix worked. Only diffing the frame data was.

**What a real repair needs.** Fuzzing a different, legal attribute such as
`DISABLE_JTAG` would produce a bit, but it lands somewhere else and
`cfg/Makefile` pins the location with `--dword 67 --dframe 1B --dbit 18`. A wrong
delta does not fail loudly — it yields a confidently wrong base address for the
tile. Re-deriving those deltas needs a bootstrap that does not depend on the
base address being measured. Copying xc7s50's value is not an option either:
different die, different frame layout. Leaving the tile uncharacterised is the
honest outcome until that work is done.

### A latent upstream bug: string-sorted site names

`add_tdb.py` failed outright with

```
AssertionError: ('CLK_BUFG_BOT_R_X52Y48', 106, 98, 8, 'CLB_IO_CLK')
```

offset 98 plus 8 words overruns the 101-word frame. The cause is that several
`005` sub-fuzzers pick their target with `sorted(sites)[0]` — a *string* sort of
site names. That is only the tile's lowest-numbered site while every index has
the same number of digits.

Sweeping the basicdb for tiles where string order and numeric order disagree
turns up exactly five, and they are precisely the tiles that caused trouble:

```
CLK_BUFG_BOT_R_X52Y48   BUFGCTRL  string=X0Y10  numeric=X0Y3
LIOI3_X0Y9              IDELAY    string=X0Y10  numeric=X0Y9
RIOI3_X31Y9             IDELAY    string=X1Y10  numeric=X1Y9
LIOB33_X0Y9             IOB       string=X0Y10  numeric=X0Y9
RIOB33_X31Y9            IOB       string=X1Y10  numeric=X1Y9
```

It is latent on xc7s50: its `CLK_BUFG_BOT_R` starts at `BUFGCTRL_X0Y0`, where
string and numeric order agree.

**Fixing it is necessary but not sufficient for `CLK_BUFG_BOT_R`.**
`clk_bufg/top.py` now sorts numerically (see `natural()` there), which moves the
selected site from `X0Y10` to `X0Y3` and the solved word from 98 to 94. The tile
actually starts at 93. The remaining word is structural: this die's
`CLK_BUFG_BOT_R` holds 13 BUFGCTRLs starting at `X0Y3`, where xc7s50's holds 16
starting at `X0Y0`, and Series-7 packs two BUFGCTRLs per configuration word — so
`X0Y3` sits `floor(3/2) = 1` word into the tile. `clk_bufg`'s
`GENERATE_ARGS` pins `--dword 0`, i.e. it assumes the selected site is at the
tile's first word, and on this die no BUFGCTRL is.

`CLK_BUFG_TOP_R` is unaffected — its lowest site, `BUFGCTRL_X0Y16`, *is* at its
tile's first word — so the two tiles need different deltas and the Makefile has
room for one. `env/clk_bufg_tdb.sh` runs the fuzzer twice and takes each tile
from the run whose delta is right for it. Both runs measure the same raw bits
(BOT_R word 094, TOP_R word 000), so this picks the correct interpretation of one
measurement rather than inventing a number — deliberately not a hand-edited tdb.

Result: `BOT_R` offset 93, `TOP_R` offset 0, identical to xc7s50, with
93 + 8 = 101 filling the frame exactly and pairing with `TOP_R` across the half
boundary.

### Two traps in `add_tdb.py`

Check both when the fan-out finishes, before trusting `tilegrid_tdb.json`.

**It skips missing tdb files silently.** `add_tdb.py` iterates a hardcoded list
of sub-fuzzer directories and does `if not os.path.exists(tdb_fn): continue`
(printing only under `--verbose`). A sub-fuzzer that died leaves its tiles with
no `bits` at all, and the build still succeeds. So verify all 21 tdbs exist and
are non-empty *before* `add_tdb.py` runs:

```bash
ls */build_$XRAY_PART/segbits_tilegrid.tdb | wc -l     # expect 21
find . -name segbits_tilegrid.tdb -empty               # expect nothing
```

**Frame counts are hardcoded per sub-fuzzer and may not fit a smaller die.**
`add_tdb.py` passes fixed `(frames, words)` pairs — `("iob", 42, 4)`,
`("clb", 36, 2)`, `("bram_block", 128, 10)` and so on — and
`util.add_tile_bits` only *warns* when `frames` exceeds what the part's
`part.yaml` allows, silently clamping to the maximum. xc7s25 is half the size of
the xc7s50 these constants were tuned on, so grep the `add_tdb.py` output for
`Warning: The number of frames` and treat any hit as a real finding rather than
noise.

### Deriving `XRAY_IOI3_TILES` — solved

**`XRAY_IOI3_TILES="LIOI3_X0Y9 RIOI3_X31Y9"`**, from measurement.

This could not be copied and should not have been guessed. `spartan7.sh`'s own
comment says it "needs to be changed for any new device", and
`generate_full.py:propagate_IOI_Y9` shows what it means: it names the IOI3 tiles
whose frame address sits one frame higher than the rest of their column, and
synthesises their entry from the previous same-type tile, forcing `words=4,
offset=18`.

**What the anomaly actually looks like — and a correction.** My first detector
looked for a tile whose `baseaddr` deviated from its column. That finds nothing,
because the fix-up erases the deviation: in
`prjxray-db/spartan7/xc7s50/tilegrid.json` the whole column interpolates
perfectly, so the published database cannot tell you which tile was anomalous.
In the *raw* data these tiles are not wrong, they are **absent** — no row at all.

I first explained that absence as "the toggled bit is a frame away from where
segmatch looks". That explanation is probably wrong. The likelier cause is the
string-sort bug described under *A latent upstream bug* below: `LIOI3_X0Y9`
contains `IDELAY_X0Y9` and `IDELAY_X0Y10`, and `sorted()` returns `X0Y10` first
because `"1" < "9"`, so the fuzzer LOCs into the neighbouring tile and the tag
never matches the bit. The `Y9` tiles are the only ones on this die whose site
pair straddles the 9-to-10 digit boundary, which is exactly why they, and only
they, fail to solve. Upstream's comment that these tiles "have the frame address
1 frame higher than the rest" may itself be a misdiagnosis of the same bug.

This does not change the answer, which was checked rather than assumed. Our
solved offsets match xc7s50's published values exactly — Y1:2, Y3:6, Y5:10,
Y11:22, Y15:30 — and Y9's correct value is 18, precisely what
`propagate_IOI_Y9` hardcodes. The final database has `LIOI3_X0Y9` at offset 18,
sitting on the arithmetic progression 10 → 18 → 22.

So the test is a set difference — every IOI3 tile in the basicdb, minus every one
the `ioi` sub-fuzzer solved:

```
## LIOI3: 36 tiles, 35 solved, 1 unsolved
   LIOI3_X0Y9           grid_x=1    grid_y=94
## RIOI3: 18 tiles, 17 solved, 1 unsolved
   RIOI3_X31Y9          grid_x=100  grid_y=94
```

Exactly one per column, both at Y9, both at `grid_y=94`. The word progression
confirms it independently: `LIOI3_X0Y5` solves to word 013 and `LIOI3_X0Y11` to
word 025, i.e. 013 + 4x3, the regular spacing continuing straight through the
gap where Y7 and Y9 would sit.

xc7s50's published value is `LIOI3_X0Y9 RIOI3_X43Y9`, which agrees positionally
(its right-hand column is X43, xc7s25's is X31). That agreement is a check on the
result, not its source.

`env/find_ioi3_anomaly.py` implements the set difference and warns if it finds
anything other than exactly one unsolved tile per column. It keeps the old
baseaddr scan as a secondary, post-`add_tdb` sanity check, where it is a valid
test of a different property.

### 3. Wire graph — `072-ordered_wires` and `074-dump_all`

Neither fuzzer writes a bitstream; they only query Vivado for tiles, wires,
nodes and PIPs, so they are slow but not delicate. 074 cannot start until 072
has run — its `generate_after_dump.sh` reads
`../072-ordered_wires/build_${XRAY_PART}/specimen_001/`. `env/run_072_074.sh`
runs the pair in that order.

The output that matters downstream is **`tileconn.json`**, the per-fabric wire
graph. 074 also writes `node_wires.json`, which nextpnr's chipdb generator does
not read at all, and family-level `tile_type_*.json` / `site_type_*.json`.

**Do not run 074's `pushdb`.** Its recipe is

    cp $(BUILD_DIR)/output/tile_type_*.json ${XRAY_FAMILY_DIR}/

and in this overlay every family-level file is a symlink into the read-only
`prjxray-db`, so that `cp` writes *through* into the reference. `env/push_074.sh`
does the same job safely: it unlinks before copying, and afterwards asserts that
nothing under `prjxray-db` changed.

Its summary is also a result in itself. Of the family-level files it pushes,
**all 151 that also exist upstream are identical in content** and only 3 are new
(the `MONITOR_*_FUJI2` types). So an independent run of 074, on a different die,
under Vivado 2026.1.1 rather than the pinned 2017.2, reproduced upstream's
spartan7 tile and site data exactly — which is about as good a check on the
whole fuzzer chain as is available without hardware.

Compare by content, not bytes: these are JSON written by different runs, so key
order and spacing differ freely. A byte compare called all 147 shared files
"different" when every one was in fact identical.

This matters beyond bookkeeping, because `build_nextpnr_s25.sh` builds **xc7s50
and xc7z010 against this same overlay**. Their chipdbs read whatever lands here.
That is safe precisely because the content matches; if the summary ever reports
a real difference, xc7s50 must be built against `prjxray-db` instead — the same
distinction `bitstreams/build_arty_s7.sh` already makes for `fasm2frames`.

#### Could xc7s50's `tileconn.json` just be reused?

Worth asking, because 072+074 are hours of Vivado. `tileconn.json` contains no
tile instance names — each entry is `(tile_types[2], grid_deltas[2]) ->
wire_pairs`, and nextpnr's `apply_tileconn()` indexes it as
`ttn[typeA][dx, dy][typeB]`. It is therefore a property of the family's tile
*types*, not of the die, and it transfers exactly when every lookup the new die
performs is one the source die also performed.

`env/check_tileconn_cover.py` answers that. Note the probe set is **not** every
adjacency in the grid: only the `(dx, dy)` registered for that `typeA`. Against
xc7s50, xc7s25 comes out almost entirely covered — 684 of xc7s50's 748 connected
shapes occur, 16968 connections applied — with exactly one class of exception:

| unexplained misses | 25, all involving `MONITOR_BOT/MID/TOP_FUJI2` |
| --- | --- |
| tile types with no `tile_type_<T>.json` | the same three |

The XADC/system-monitor column is a **different tile type on this die**:
xc7s50 has `MONITOR_BOT` / `MONITOR_MID` / `MONITOR_TOP`, xc7s25 has
`MONITOR_BOT_FUJI2` / `MONITOR_MID_FUJI2` / `MONITOR_TOP_FUJI2`, and no shipped
Series-7 family in `prjxray-db` — artix7, kintex7, spartan7, zynq7 — carries a
`tile_type_MONITOR_*_FUJI2.json`.

That decided it: reuse would leave the XADC column with no wires, and silently,
because `read_tile_type_json()` returns `None` for a missing type without
complaining. So 074 was run for real. Afterwards the coverage probe reports
**0 unexplained misses and 0 tile types without JSON**, and 17020 connections
applied against the borrowed file's 16968 — the 52 extra are that column.

What this buys is that the column is *present and routable through*, not that an
XADC can be instantiated: nextpnr ships no `site_type_XADC.json` in **any**
family (only `pins.cc` knows the primitive, for its invertible pins), so the
XADC site has no bel regardless of the database. That is an upstream limit, not
something the characterisation left out. The check is kept because it is the right
first question for the next die, and because it is what found the FUJI2 naming.

`finish_074_s25.sh` re-runs it afterwards in two directions: the new file
against this die (where no miss can be "unexplained" by construction, but the
`tile_type_<T>.json` half of the report still proves the FUJI2 hole is closed),
and xc7s50's file against this die again, from **xc7s50's own grid** — pointing
the baseline at this die's grid instead makes source and subject identical and
reports nothing at all.

#### `generate_grid.py` caught a real bug in our own tilegrid

074 does not only produce data, it *checks* ours. `generate_grid.py` rebuilds
the tilegrid from its own Vivado dumps and asserts it against the one
`005-tilegrid` wrote. On xc7s25 that assertion fired:

    AssertionError: ('BRAM_L_X6Y45', 'sites',
        {... 'RAMB36_X0Y9': 'RAMB36E1'},      <- ours, from 005
        {... 'RAMB36_X0Y9': 'RAMBFIFO36E1'})  <- 074's, from its own dump

A Series-7 site can have several possible `SITE_TYPE`s and Vivado reports
whichever is currently selected, so 005 records whatever selection its design
happened to leave behind. It caught **8 of the 45** BRAM tiles in the
`RAMB36E1` selection and the other 37 in `RAMBFIFO36E1` — internally
inconsistent, which is the tell that ours is the wrong one. Three independent
things agree on `RAMBFIFO36E1`:

* every shipped `prjxray-db` tilegrid is uniform in it — spartan7/xc7s50 75/75,
  artix7/xc7a50t 75/75
* 074, dumping the same die separately, says `RAMBFIFO36E1` for all 45
* nextpnr ships `meta/spartan7/site_type_RAMBFIFO36E1.json` and **nothing** for
  `RAMB36E1`

That last point is why this is a defect and not a cosmetic difference:
`read_tile_type_json()` returns `None` for a site type it has no metadata for
without complaining, so those 8 BRAM tiles would have come out with no RAMB36
site at all. The same silent failure mode as the `MONITOR_*_FUJI2` gap — and it
was already baked into the chipdb built before this was found, which is the
argument for rebuilding rather than assuming the old one was fine.

And it was not one site. Fixing the RAMB36 tiles only moved the assertion to
the next one, so `env/sync_tilegrid_sites.py` does the general job: it calls the
same `generate_tilegrid()` that `generate_grid.py` uses (about half a minute),
diffs the whole thing, and reports every difference at once. On xc7s25, **22
site types across three families** were wrong:

| ours | 074, the references, nextpnr's metadata | count |
| --- | --- | --- |
| `RAMB36E1` | `RAMBFIFO36E1` | 8 of 45 |
| `BUFG` | `BUFGCTRL` | 3 of 32 |
| `IOB33` | `IOB33M` | 6 |
| `IOB33` | `IOB33S` | 5 |

The IOB33 ones are the worst of the three, because `site_type_IOB33.json` *does*
exist in nextpnr — so instead of getting no site, those 11 pads would have
loaded the wrong site's bels and pins. After the fix our counts match the
reference structure: `IOB33M`/`IOB33S` balanced at 72/72 plus 6 plain `IOB33`
for the single-IOB `SING` tiles, exactly the shape xc7s50 has at 120/120 plus 10.

The script rewrites **only** the `sites` values, where the cause and the right
answer are both known; a difference in any other field is printed and left
alone, because that would mean something else is wrong and wants looking at
rather than papering over. It reproduces prjxray's exact JSON formatting
(`indent=4`, `sort_keys=False`, trailing newline — verified by round-tripping
the file unmodified), so the only diff is the values it means to change.
Rewriting the data rather than re-running 005 is deliberate: 005 is hours of
Vivado, and the right values are known three ways over.

#### The node verification needs a per-part `ignored_wires.txt`

`generate_grid.py` and `check_nodes.py` both finish by rebuilding every node
from tileconn and comparing against what Vivado reported, and a residue of
disagreements is normal. Upstream handles it with a per-part whitelist at
`fuzzers/074-dump_all/ignored_wires/<family>/<part>_ignored_wires.txt`. There is
none for `xc7s25csga324-1`, so the first run reported all 474 and stopped.

They are the standard family. Every whitelist upstream ships is dominated by the
clock-capable-IO to global-clock path — `I2GCLK` and `CCIO`:

| part | I2GCLK/CCIO | total |
| --- | --- | --- |
| xc7s50fgga484-1 | 100 | 110 |
| xc7a50tfgg484-1 | 100 | 110 |
| xc7z010clg400-1 | 40 | 44 |
| xc7k160tffg676-2 | 160 | 176 |

What makes them ignorable rather than merely common is their *shape*, and
`prjxray.lib.check_errors` is strict about it: for each disagreeing node it
takes the largest reconstruction as correct and asserts every other one is a
**single stranded wire**. A node genuinely split in two trips that assert and no
whitelist can silence it. `env/gen_ignored_wires.py` derives the file using that
same rule, and refuses — rather than writing — if anything is not a stranded
single.

On xc7s25 it produced 66 wires with the same six families as upstream's xc7s50
file, in the same proportions, scaled to the smaller die:

    LIOI_I2GCLK_TOP      20  (xc7s50: 30)   CMT_PHASER_UP_DQS_TO_PHASER_D    3  (5)
    LIOI_I2GCLK_BOT      20  (        30)   CMT_PHASER_DOWN_DQS_TO_PHASER_A  3  (5)
    RIOI_I2GCLK_TOP      10  (        20)
    RIOI_I2GCLK_BOT      10  (        20)

and the rerun reported *474 errors ignored*, with `check_nodes.py` then passing.

#### Never re-run `generate_after_dump.sh` to recover

Its third line is `rm -rf ${BUILD_DIR}/output`. It is also `set -e`, so a
failure part-way leaves everything earlier intact — on xc7s25 that is about six
hours of work: `nodes.db` (285 MB), `nodes.pickle` (154 MB), `node_tree.json`
(313 MB), 111 `tile_type_*.json` and 39 `site_type_*.json`. Re-running the
wrapper to "try again" deletes all of it first. `env/resume_074_s25.sh` re-runs
only the remaining steps, with the arguments the wrapper uses.

A related trap when watching from outside: `pgrep -f generate_after_dump.sh`
matches the *watcher's own* command line, so a monitor built that way reports
the fuzzer as alive indefinitely after it has died. Bracket the pattern —
`pgrep -f '[g]enerate_after_dump.sh'`.

### 4. chipdb

`himbaechel/uarch/xilinx/gen/xilinx_gen.py` reads, from `<db>/spartan7`:
`<fabric>/tilegrid.json`, `<fabric>/tileconn.json`, each part's
`package_pins.csv`, the family `tile_type_*.json`, and nextpnr's own
`meta/spartan7/` site metadata. Everything but the metadata is ours.

`xc7s25` had to be added to `ALL_HIMBAECHEL_XILINX_DEVICES`. No alias was added:
the part-name regex already parses `xc7s25csga324-1` since the Spartan-7 commit,
and it resolves to its own die, which is correct — xc7s25 and xc7s50 are
different dies, unlike the `xc7a35t -> xc7a50t` and `xc7z007s -> xc7z010` pairs.

`env/build_nextpnr_s25.sh` builds it, pointed at the overlay rather than at
`prjxray-db`, with `HIMBAECHEL_SPLIT=ON` so the binary is named
`nextpnr-himbaechel-xilinx` — matching the WASI build it is diffed against.

One trap: cmake's bba rule lists only `xilinx_gen.py` and `constids.inc` as
`INPUTS`, so **changing the database does not invalidate the chipdb**. Re-running
074 and rebuilding would silently keep the old one. Both build scripts take
`FORCE_CHIPDB` to delete it first. It takes a `;`-separated device list, or `1`
for all of them — worth naming, because xc7s50's `.bba` alone is 116 MB and
regenerating it because *xc7s25's* database moved costs minutes twice over
(native and WASI).

#### The whole post-074 chain: `env/finish_074_s25.sh`

Push, coverage re-check, chipdb, bitstream, WASM package — in that order, with
each step's trap encoded rather than remembered. Steps are selectable
(`env/finish_074_s25.sh bitstream`), which is how the traps below were found by
running them against the interim database before 074 had finished.

Two things it refuses to do:

* **Push before 074 is finished.** `tileconn.json` appearing is not the finish
  line — `generate_grid.py` writes it, and `node_names.py` and `check_nodes.py`
  still run afterwards, `check_nodes.py` being the step that validates what was
  just built. The step checks for a live `generate_after_dump.sh` and for
  `check_nodes` in the log.
* **Count frames from `blink.frames`.** This one produced a convincing false
  alarm: `wc -l blink.frames` is **2622**, while the finished bitstream has
  **3060**. `fasm2frames` emits only the frames it actually set bits in;
  `xc7frames2bit` pads the die out to its full complement. The intermediate
  measures the *design*, the `.bit` measures the *device*. The frame count must
  come from `bitread`.

## WebAssembly

`0-xilinx-bits/wasm-build/build_nextpnr_xilinx_wasm.sh` builds
nextpnr-himbaechel-xilinx as a WASI command;
`hotc/web/nextpnr-xilinx-wasm/` packages it for the browser. The recipe is
YoWASP's (`github.com/YoWASP/nextpnr`, `build.sh`) — wasi-sdk, Boost built for
wasm32, Eigen 3.4 — but with our nextpnr tree rather than YoWASP's pinned one,
because Himbächel validates the chipdb against the binary and YoWASP's pin has
neither the Spartan-7 part-name parsing nor xc7s25.

The chipdb is deliberately **not** linked in: `-DEXTERNAL_CHIPDB=ON
-DEXTERNAL_CHIPDB_ROOT=/share` leaves `chipdb-xc7s25.bin` (20 MB against a
2.3 MB module) a separate file, fetched into the WASI filesystem at run time.

Four things in that recipe do not survive contact with current nextpnr and
current wasi-sdk, and all four fail in ways worth writing down.

**`std::mutex` does not exist.** Boost's `error_category_impl.hpp` uses it
unless told otherwise, so `libboost_filesystem` will not compile without
`-DBOOST_NO_CXX11_HDR_MUTEX`. Upstream's script passes this only on its
single-threaded branch, which is easy to lose when inlining that branch.

**nextpnr's own no-threads switch did not fire.** `NPNR_DISABLE_THREADS` is
gated on `CMAKE_SYSTEM_NAME STREQUAL "WASI"`, but YoWASP's toolchain file sets
`Generic` and signals WASI through a separate `WASI` variable — an older
nextpnr keyed off exactly that variable. Under `Generic`, `find_package(Threads)`
succeeds against the *host* pthreads and the build dies in `placer1.cc` on
`std::lock_guard`. Setting `CMAKE_SYSTEM_NAME` to `WASI` fixes it and also turns
on `-lwasi-emulated-mman`, which is needed anyway. On wasi-sdk 34 a second
prop is required: wasm32-wasip1 ships a stub `libpthread`, so `find_package
(Threads)` succeeds there too and nextpnr then demands a Boost `thread`
component; `-DCMAKE_DISABLE_FIND_PACKAGE_Threads=ON` makes the answer match
reality.

**`std::lock_guard` does not exist either.** wasi-sdk's libc++ compiles
`lock_guard` and `unique_lock` out of `<mutex>` entirely when built without
threads — they are not merely unusable, they are undeclared — yet the placer and
routers take the Context lock unconditionally. Four sites: `placer1.cc`,
`router1.cc`, `router2.cc`, `placer_heap.cc`. `common/kernel/npnr_lock.h` (new,
local) aliases `ScopeLock`/`ScopeUniqueLock` to the `std::` types normally and
to do-nothing stand-ins under `NPNR_DISABLE_THREADS`. That substitution is exact
rather than approximate: in that configuration `BaseCtx::lock()`/`unlock()` have
empty bodies, so the real guards already acquire nothing.

**Exceptions cannot be had at all.** This is the one with a real cost.

* nextpnr throws — `log_error` does, and 45 of the 57 objects here reference
  `__cxa_throw`.
* **wasi-sdk 22 defines `__cxa_throw` in no library, for any of its targets.**
  Checked exhaustively, not assumed. So the version pinned in upstream's script
  cannot link current nextpnr at all.
* wasi-sdk 34 ships `eh/` and `noeh/` sysroot variants, and with
  `-fwasm-exceptions -lunwind` a C++ throw/catch really does work — verified by
  running one under Node.
* But a module built that way uses the WebAssembly exception-handling proposal,
  and **jco refuses to transpile it**: *"exceptions proposal not enabled"*. jco
  is how the module becomes something `@yowasp/runtime` can run, which is how it
  reaches the browser. Upgrading jco 1.3 → 1.34 gets `jco new` past it and
  `jco transpile` still refuses.

So the module is built without exception handling, and
`wasm-build/wasi_throw_stubs.cc` supplies the `__cxa_*` runtime the linker wants,
with `__cxa_throw` calling `exit(1)`. This is sound here only because **no throw
in this build is recoverable**: every catch site — `command.cc` and `placer1.cc`
on `log_execution_error_exception`, `himbaechel/arch.cc`'s `catch (...)` around
opening the chipdb, `util.h` on `std::invalid_argument` — responds by calling
`log_error`, which is itself fatal. Nothing catches and carries on, so no
successful run reaches a stub. The error text is not lost either, since
`log_error` prints before it throws; what is lost is the epilogue and the
unwind. `exit(1)` rather than `abort()` gives the host a clean status instead of
a trap.

This is the same bargain YoWASP strikes — their nextpnr cannot throw either —
and it is why their `build.sh` sets `-DBOOST_NO_EXCEPTIONS`, which current
nextpnr's CMakeLists has dropped.

The standing guard against the bargain going bad is
`hotc/web/nextpnr-xilinx-wasm/diff_native.mjs`, which runs the same design
through both builds and compares.

It does **not** compare byte for byte, and it does **not** compare feature
counts. Both were tried and both are wrong, the second more subtly than the
first.

Each build is deterministic on its own — run either twice with the same seed and
the FASM is identical — but they differ from each other, structurally, because
wasm32 has 32-bit `size_t` and pointers. nextpnr's hash values, and so the
iteration order of the containers the packer and the router walk, are not the
same as on x86-64. Two consequences, both legal:

* cells land on different LUTs within a slice **and on different input pins**,
  which changes the LUT `INIT` *bits*. Same function, different encoding:
  `fasm.cc`'s `get_lut_init()` reads the cell's logical `INIT` and permutes it
  by the `X_ORIG_PORT_A*` pin mapping at write time.
* the router picks different paths. On xc7s25 the `INT_L` PIP count happened to
  net to zero — four adjacent tiles trading +1/−1/−1/+1. **That was a
  coincidence, and asserting it as a law is what broke when xc7s50 was added**:
  there the clock takes HROW track `CK_IN_L8` instead of `CK_IN_L7` and the
  total differs by one, failing three checks on a build that was fine.

So the test now asserts what survives that. The strongest of them is the
**post-PnR netlist**, written with `--write` from both builds: the same
cell-type multiset and the same `(type, INIT)` multiset. Because that `INIT` is
the logical truth table straight from synthesis, *before* any pin permutation,
two builds agreeing there have packed the same logic. On xc7s50 it matches
exactly while 143 FASM features differ.

Alongside it: each build reproduces itself; the staged chipdb is asserted byte-identical to the native one (the only check that catches a *stale* staged copy, since cmake's bba rule does not depend on the database); nextpnr's own utilisation report
matches (51 rows — note nextpnr logs to **stderr**, so capturing only stdout
compares nothing and passes vacuously); the same number of LUTs is configured;
logic tiles are used identically instance by instance; IO is byte-identical
(LOC-constrained by the XDC, not the placer's choice); routing is within a 10%
tolerance rather than equal; and the WASM FASM is carried through `fasm2frames`
→ `xc7frames2bit` → `bitread` to a valid bitstream.

| part | FASM lines differing | INT PIPs native/wasm | bitstream from the WASM FASM |
| --- | --- | --- | --- |
| xc7s25csga324-1 | 61 of 519 | 155 / 155 | 2622 frames written, 3060 in the die |
| xc7s50csga324-1 | 80 of 511 | 145 / 146 | 4970 written, 5408 |
| xc7z007sclg400-1 | 0 of 579 | 180 / 180 | 2952 written, 5144 |

Two traps in that last column. `fasm2frames` exiting 0 is **not** enough: handed
an empty frames file — which is what it leaves behind when it fails on a missing
`mapping/devices.yaml` — `xc7frames2bit` pads the die out to a full all-zero
bitstream, reports a perfectly normal frame count and prints `DONE`. And the
count of lines in `blink.frames` is not the frame count: it is the frames the
*design* touched, while the `.bit` carries the whole *device*.

What the test cannot do: tell a hash-order difference from a cost-function
difference, because both produce legal results. The tolerance is the only
quality signal. It distinguishes a broken port from a working one, which is
what it is for.
